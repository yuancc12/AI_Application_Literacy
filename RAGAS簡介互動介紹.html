安裝：三分鐘開工

Python 3.9 以上。RAGAS 本身不帶模型，大部分指標要一個「評審 LLM」，記得設定 API 金鑰，也可以接 Anthropic、Gemini 或本地 Ollama。

1. 安裝套件



2. 設定評審金鑰
# 預設範本用 OpenAI
export OPENAI_API_KEY="sk-..."

# 停用匿名使用統計（選用）
export RAGAS_DO_NOT_TRACK=true


3. 確認版本
python -c "import ragas; print(ragas.__version__)"
# 0.4.4


quickstart 範本會產生 rag.py（你的 RAG）、evals.py（評估流程），結果存到 evals/experiments/。









準備資料：評審要看的四樣東西


每一筆評估資料，就是關係圖上的四個節點。最容易搞混的是：其中兩樣由你事先準備，另外兩樣是你的 RAG 跑出來的。




你事先準備 測試集
user_input 問題、reference 標準答案。存成 CSV，一份測試集可以重複用來評每個版本。


RAG 執行時產生 每次重跑
retrieved_contexts 檢索內容、response 回答。每次改設定都要重新跑，才知道新版本的表現。






user_inputQuery · 字串 · 你準備
使用者會問的問題，照真實口吻寫。
"台北101何時完工？"
好：從客服紀錄、搜尋紀錄挑真實問題
避免：全是你自己想的簡單題


retrieved_contextsContext · 字串清單 · RAG 產生
檢索器找回、真正塞進 prompt 的段落，依排名順序。
["台北101於2004年完工，高508公尺。", "..."]
好：存段落原文，保留順序
避免：只存文件 ID 或整份文件


responseResponse · 字串 · RAG 產生
RAG 最後給使用者的回答，一字不改。
"台北101於2004年完工。"
好：存最終輸出，含格式
避免：手動修飾過的回答


referenceGround Truth · 字串 · 你準備
正確、完整的標準答案，最好由懂業務的人寫。
"台北101於2004年完工。"
好：寫成完整句子，涵蓋所有重點
避免：只寫「是」、「2004」這種片段

上線前檢查清單


    

  • 題數夠嗎？建議先從 50 題左右起步，太少的話一兩題就能讓平均分數大幅波動。
    • 

  • 題型有涵蓋嗎？簡單事實題、需要整合多段的題、知識庫查不到的題（應該回答「不知道」）都要有。
    • 

  • 標準答案可信嗎？由懂業務的人寫或審，資料更新時一併更新。
    • 

  • 合成題目抽查過嗎？TestsetGenerator 產生的題目與答案要人工抽查，刪掉不自然或錯誤的。
    • 

  • 檢索內容存原文嗎？存實際塞進 prompt 的段落文字與順序，不是文件名稱。
    • 

  • 版本有記錄嗎？每次實驗一起記錄模型、chunk 大小、top-k、prompt 版本，之後才能比較。
    • 



清單中的題數與題型是一般實務建議，請依你的場景調整。







使用：從一筆資料到整個測試集


0.4 版從 ragas.metrics.collections 匯入指標，舊的 evaluate() 寫法官方已列為淘汰、1.0 移除。圖上的舊名稱對照新類別：answer_similarity → SemanticSimilarity，其餘改成大駝峰，例如 context_recall → ContextRecall。


    

    

    


    

    六個指標的數學公式
    

    每張卡片下方的灰色區塊，是把下一節範例資料集第 2 題代入公式的計算過程。可以在下一節切換題目，代入的數字會跟著變。
    

    context_precision① 檢索精準度
    Context PrecisionK=∑k=1K(Precision@k×vk)前 K 段中的相關段落數Precision@k=TPkTPk+FPk
    vk：第 k 段是否相關（1 或 0）；TPk、FPk：前 k 段中相關／不相關的段數。相關段落排越前面，分數越高。
    context_recall② 檢索召回率
    Context Recall=|標準答案中能由檢索內容支持的陳述||標準答案的全部陳述|
    先把標準答案拆成陳述句，再逐條檢查能否在檢索內容中找到依據。
    faithfulness③ 忠實度
    Faithfulness=|回答中能由檢索內容支持的陳述||回答的全部陳述|
    先把回答拆成陳述句，再逐條檢查能否由檢索內容推得。對的但內容沒寫，也算不支持。
    answer_relevancy④ 回答切題度
    Answer Relevancy=1N∑i=1Ncos(Egi,Eo)
    評審 LLM 從回答反推 N 個問題 gi（預設 N = 3）；E 是 embedding 向量，Eo 為原問題的向量。
    answer_correctness⑤ 回答正確性
    Answer Correctness=w1⋅F1fact+w2⋅cos(Er,Egt)F1fact=|TP||TP|+12(|FP|+|FN|)
    預設 w1 = 0.75、w2 = 0.25。TP：兩邊都有的事實；FP：回答有、標準答案沒有；FN：標準答案有、回答漏掉。
    answer_similarity⑥ 語意相似度
    Answer Similarity=cos(Er,Egt)=Er⋅Egt‖Er‖‖Egt‖
    Er：回答的向量；Egt：標準答案的向量。0.4 版類別名為 SemanticSimilarity，只用 embeddings，不需評審 LLM。

    評分實驗室
    

    兩個最常被問的指標，親手玩一次就懂。
    

    實驗一：Faithfulness 蓋章現場
    

    

    

    Context：台北 101 於 2004 年完工，高 508 公尺，曾是世界最高建築。
    Response：
      

      faithfulness
      0
      

      

      實驗二：answer_correctness 調配器
      

      

      answer_correctness 是兩把尺的加權：事實比對（陳述句的 F1）佔 0.75，語意相似度（embeddings）佔 0.25。拉拉看。
      

      

      

      試試：相似度拉滿、F1 拉低。講得很像但事實錯，分數照樣上不去。
      

      answer_correctness
      0
      

      

      


      

      分數判讀：哪把尺量出問題，就修哪一段
      

      

      指標偏低可能原因調整方向
      


      context_precision雜訊多、相關段落排太後面加 reranker、用 metadata 過濾
      

      context_recall該找的段落沒找到調 chunk 大小、換 embedding 模型、加大 top-k、混合檢索
      

      faithfulness模型自行補充內容（幻覺）prompt 要求只依據提供內容、降低 temperature、換模型
      

      answer_relevancy答非所問、太冗長調整 prompt 與輸出格式、改寫使用者問題
      

      answer_correctness事實錯誤或漏掉重點先看前四項定位；若 faithfulness 高仍偏低，多半是知識庫錯誤或過期
      

      answer_similarity說法和標準答案差很多單看它容易誤判，搭配 answer_correctness 一起看
      

      

      

      一次只改一個變因
      建測試集、跑基準線、改一個設定、比較，再放進 CI 擋下退步。
      

      評審也會看走眼
      固定評審模型與版本，定期抽樣人工複核，確認分數跟人的判斷一致。
      

      還有更多尺
      進階 RAG 指標有 Context Entity Recall、Noise Sensitivity（越低越好）；另有 Agent 工具呼叫、BLEU/ROUGE、自訂規則等類別。
